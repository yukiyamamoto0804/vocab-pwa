# 基本ルール（設計・実装の前提）

このプロジェクトの全ての設計・実装はこのルールに従う。
ルールを変える場合は、先にこのファイルを更新してから実装する。

---

## 0. 目的

- ユーザーが自分で用意した教材（単語リスト・音声など）を取り込んで学習する、スマホ向けの単語帳 PWA を作る。
- 個人用に作るが、特定の教材に依存しない汎用ツールとして設計する。
- スマホ（iOS / Android）で、オフラインでも使えること。
- ソースコードは公開できる状態を保つこと。

## 1. 最重要原則：コードと教材を完全に分離する

| | アプリ本体（コード） | 教材データ |
|---|---|---|
| 中身 | UI・学習ロジック・取り込み処理 | 単語リスト、訳、例文、音声など |
| 権利 | 自分 | 教材の権利者 |
| 置き場所 | GitHub（公開） | 自分の端末のみ |
| Git | 管理する | **絶対にコミットしない** |

- アプリは「決められた形式の教材パックを読み込む器」として作る。
- 教材の中身（単語・訳・例文・音声）をソースコード、テスト、サンプル、コメント、コミットメッセージ、Issue に**書かない**。
- テストやサンプルには、自作のダミーデータまたはオープンライセンスのデータ（例: NGSL / CC BY-SA）だけを使う。使う場合は出典とライセンスを明記する。

## 2. 著作権ルール

- 教材は、ユーザーが正当に入手したものを**自分の学習のためだけに**取り込む前提とする（私的使用の範囲。著作権法30条）。
- 教材データを**公開・共有・配布しない**。対象は公開リポジトリ、公開サーバー、共有リンク、他人の端末。
- 単語そのものに著作権はないが、書籍などの**選定・順序・訳・例文・音声**は保護されうるものとして扱う。
- コピーガード（DRM）がかかったデータの保護を回避しない。
- 判断に迷うものは「公開しない側」に倒す。

## 3. デプロイ方針

```
GitHub（公開・コードのみ）
  → GitHub Pages（公開・アプリの器のみ）
     → スマホのブラウザで開いて「ホーム画面に追加」（PWA）
        → 教材パック(zip)をファイル選択で取り込み → 端末内に保存
```

- **公開サーバーには教材を一切置かない。** ビルド成果物に教材が混入しないことを確認する。
- 配信先は GitHub Pages。`main` に push すると、GitHub Actions（`.github/workflows/deploy.yml`）が lint・テスト・ビルドを行い、`dist/` だけを配信する。無料で HTTPS が付き、リポジトリと同じ場所で設定が完結するため。
  - 初回だけ、リポジトリの Settings → Pages → Build and deployment の Source を「GitHub Actions」にする。
- 端末内のデータ（教材・学習記録）は、配信先のオリジン（`https://<ユーザー>.github.io`）ごとに保存される。独自ドメインや別のホスティングに移すと、それまでのデータは見えなくなる。リポジトリ名を変えると、ホーム画面に追加したアプリの URL が変わり、追加し直しが必要になる。**配信先の URL を変える前に、必ず学習記録をエクスポートする。**
- 同じユーザーのほかの GitHub Pages サイトと同じオリジンを共有するため、IndexedDB のデータベース名はアプリ固有の名前（`vocab-pwa`）にする。
- 教材パックは PC で作り、端末間のファイル共有機能やクラウドストレージなどでスマホに渡して、アプリの「取り込み」機能で読み込む。
- 保存先はブラウザ内ストレージ（IndexedDB）。
- 外部サーバーへの送信は行わない（アナリティクス・外部 API も、導入する場合は先にルールを更新）。
- 将来、複数端末の同期が必要になったら「認証付きの非公開ストレージ」を追加機能として検討する（その時点でルールを更新）。

## 4. PWA / 端末まわりの必須要件

- **オフラインで完全に動作する**こと（Service Worker でアプリ本体をキャッシュする）。
- 起動時に `navigator.storage.persist()` を要求する。
- iOS Safari ではホーム画面に追加しないとデータが消えることがあるため、未追加の場合はアプリ内で案内する。
- 学習記録は**エクスポート / インポート**できること（端末にしかデータがないため、バックアップ手段は必須）。
- スマホ縦画面・片手操作を基準に UI を作る。PC でも動けばよい。

## 5. カスタマイズ性

- 教材は人が読める形式（JSON / CSV）で持ち、形式は `docs/CONTENT_FORMAT.md` に文書化する。
- 元の音声ファイルは加工しない。1 ファイルに複数項目を収録した音声にも対応するため、項目ごとの再生は「ファイル名＋開始秒〜終了秒」で指定できるようにする。
- **教材データ**と**学習記録**は分けて保存する。教材を差し替えても記録が壊れないよう、項目は安定した `id` で参照する。
- 学習アルゴリズムの設定（復習間隔、習得の基準など）は設定値として外に出し、コードにハードコードしない。

## 6. 公開リポジトリとしての衛生

- ライセンスは MIT（`LICENSE`）。
- API キー・個人情報・ローカルの絶対パスをコードに書かない。
- **開発者個人の環境・端末の情報を公開ファイルに書かない。** 例: 使っている OS・PC・スマホの機種、インストール済みのツールやバージョン、ユーザー名（著作権表示とリポジトリの URL に使う GitHub アカウント名は除く）、ディレクトリ構成。設計理由は「自分の環境ではこうだから」ではなく、一般的な理由で書く。動作要件として必要なもの（例: 対応ブラウザ、必要な Node.js のバージョン）は、要件として書いてよい。
- README に「教材データは同梱していない。自分で用意したデータを取り込んで使う」と明記する。
- ローカルの教材は全て `data/` 以下に置き、`.gitignore` で丸ごと除外する。`data/` の外に教材を置かない。

## 7. 公開ドキュメントとローカルドキュメントの分離

| | 公開ドキュメント（`docs/`） | ローカルドキュメント（`private/`、Git 管理外） |
|---|---|---|
| 書くこと | 汎用の単語帳アプリとしての設計・ルール | 自分の教材に関すること全て |
| 例 | 教材パック形式、学習アルゴリズム、画面設計 | 手元の教材の種類・形態・規模、教材に合わせた作業計画、教材パックの作り方 |

- 公開されるファイル（ドキュメント・コード・コミットメッセージ・Issue）には、**手元の教材を推測できる情報を書かない**。対象は書名・出版社だけでなく、教材の種類や形態（例: どんな形式のデータを持っているか、持っていないか）、規模、フォルダ名・ファイル名なども含む。
- 公開ドキュメントの設計理由は「汎用ツールとして必要だから」の形で書く。自分の教材の都合で決めたことは `private/` に書く。
- `CLAUDE.local.md`（Git 管理外）から `private/` を参照する。

## 8. コミット前の著作権レビュー

全てのコミットは、次の 2 段階のチェックを通す。

| 段階 | 仕組み | 内容 |
|---|---|---|
| 意味のレビュー | `copyright-reviewer` エージェント（`.claude/agents/`） | 教材の内容・教材を推測できる情報・公開経路への混入・第三者素材のライセンスを確認し、PASS ならステージ内容に対する承認を記録する |
| 機械的チェック | git フック（`scripts/git-hooks/`） | `data/`・`private/`・メディアファイルの混入、禁止語（非公開リスト）、承認の有無を確認し、問題があればコミットを止める |

- 禁止語リストは Git 管理外（`.git/info/copyright-denylist`）に置く。
- フックの回避（`--no-verify` など）は禁止。
- 新しい環境で clone した場合は `git config core.hooksPath scripts/git-hooks` を実行してフックを有効にする。

## 9. 技術スタック

| 役割 | 採用 | 選定理由 |
|---|---|---|
| ビルド | Vite | 標準的で高速。静的サイトとして配信できる |
| 言語 | TypeScript | 教材パック形式などのデータを型で検証できる |
| UI | React | 情報・ライブラリが最も多く、カスタマイズ時に調べやすい |
| スタイル | 普通の CSS（CSS Modules） | 追加ライブラリ不要。小規模アプリには十分 |
| 画面遷移 | React Router（HashRouter） | 定番で戻る操作にも対応する。ハッシュ形式の URL なら配信先のパス構成に依存しない |
| PWA | vite-plugin-pwa | Service Worker とマニフェストを生成し、オフライン動作を実現する |
| 端末内保存 | Dexie.js（IndexedDB） | 音声 Blob を保存でき、スキーマ変更（マイグレーション）が容易 |
| zip 展開 | fflate | 軽量・高速で、スマホ上での展開に向く |
| 区間再生 | Web Audio API でデコード・切り出し、`<audio>` 要素で再生（どちらもブラウザ標準） | 区間だけを WAV に切り出して最後まで鳴らすため、停止位置がずれない（`<audio>` 要素で途中から途中まで鳴らすと iOS で停止位置がずれやすい）。Web Audio API で鳴らすと、iOS ではアプリを離れて戻った後に音が出なくなる不具合がある |
| テスト | Vitest | Vite と設定を共有できる |
| テスト用の IndexedDB | fake-indexeddb（開発時のみ） | Node 上のテストで IndexedDB を再現し、Dexie を使う処理をテストできる。アプリ本体には含まれない |
| 整形・静的解析 | Biome | 整形と静的解析を 1 つのツールで行える |
| パッケージ管理 | npm | Node.js 標準のパッケージマネージャーで、追加のツールが要らない |

- 採用するライブラリは、公開リポジトリと両立するオープンソースライセンス（MIT など）のものに限る。
- ここにないライブラリを追加する場合は、先にユーザーに確認し、この表を更新する。

## 10. 開発の進め方

- 小さく作ってスマホの実機で確認しながら進める。
- 優先順位: **単語の学習** → 学習記録・復習 → その他の教材形式への対応。
- 大きな設計判断はドキュメントに残す（何を選び、なぜそうしたか）。汎用的な判断は `docs/`、教材固有の判断は `private/`。
- 画面構成・フォルダ構成・データ構造・実装の順番は `docs/ARCHITECTURE.md` に従う。
- 実装の区切りとコミットの前に、`code-reviewer` エージェント（`.claude/agents/`）でコードレビューを行う。著作権のチェック（8 章）とは別に行う。

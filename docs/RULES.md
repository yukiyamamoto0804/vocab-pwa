# 基本ルール（設計・実装の前提）

このプロジェクトの全ての設計・実装はこのルールに従う。
ルールを変える場合は、先にこのファイルを更新してから実装する。

---

## 0. 目的

- ユーザーが自分で用意した教材（単語リスト・音声など）を取り込んで学習する、スマホ向けの単語帳 PWA を作る。
- 個人用に作るが、特定の教材に依存しない汎用ツールとして設計する。
- スマホ（iOS / Android）で、オフラインでも使えること。
- ソースコードは公開できる状態を保つこと。

## 1. 最重要原則：コードと教材を完全に分離する

| | アプリ本体（コード） | 教材データ |
|---|---|---|
| 中身 | UI・学習ロジック・取り込み処理 | 単語リスト、訳、例文、音声など |
| 権利 | 自分 | 教材の権利者 |
| 置き場所 | GitHub（公開） | 自分の端末のみ |
| Git | 管理する | **絶対にコミットしない** |

- アプリは「決められた形式の教材パックを読み込む器」として作る。
- 教材の中身（単語・訳・例文・音声）をソースコード、テスト、サンプル、コメント、コミットメッセージ、Issue に**書かない**。
- テストやサンプルには、自作のダミーデータまたはオープンライセンスのデータ（例: NGSL / CC BY-SA）だけを使う。使う場合は出典とライセンスを明記する。
- 例外として、アプリと一緒に公開するデモ教材（`demo/`）は、11 章の決まりで作ったものに限って置いてよい。

## 2. 著作権ルール

- 教材は、ユーザーが正当に入手したものを**自分の学習のためだけに**取り込む前提とする（私的使用の範囲。著作権法30条）。
- 教材データを**公開・共有・配布しない**。対象は公開リポジトリ、公開サーバー、共有リンク、他人の端末。
- 単語そのものに著作権はないが、書籍などの**選定・順序・訳・例文・音声**は保護されうるものとして扱う。
- コピーガード（DRM）がかかったデータの保護を回避しない。
- 判断に迷うものは「公開しない側」に倒す。
- 11 章のデモ教材は、オープンなライセンスの材料と自作のものだけで作るので、この章でいう教材データに当たらない。

## 3. デプロイ方針

```
GitHub（公開・コードとデモ教材）
  → GitHub Pages（公開・アプリの器とデモ教材）
     → スマホのブラウザで開いて「ホーム画面に追加」（PWA）
        → 教材パック(zip)をファイル選択で取り込み → 端末内に保存
```

- **公開サーバーには教材を一切置かない。** ビルド成果物に教材が混入しないことを確認する。例外は 11 章のデモ教材だけ。
- 配信先は GitHub Pages。`main` に push すると、GitHub Actions（`.github/workflows/deploy.yml`）が lint・テスト・ビルドを行い、`dist/` だけを配信する。無料で HTTPS が付き、リポジトリと同じ場所で設定が完結するため。
  - 初回だけ、リポジトリの Settings → Pages → Build and deployment の Source を「GitHub Actions」にする。
- 端末内のデータ（教材・学習記録）は、配信先のオリジン（`https://<ユーザー>.github.io`）ごとに保存される。独自ドメインや別のホスティングに移すと、それまでのデータは見えなくなる。リポジトリ名を変えると、ホーム画面に追加したアプリの URL が変わり、追加し直しが必要になる。**配信先の URL を変える前に、必ず学習記録をエクスポートする。**
- 同じユーザーのほかの GitHub Pages サイトと同じオリジンを共有するため、IndexedDB のデータベース名はアプリ固有の名前（`vocab-pwa`）にする。
- 教材パックは PC で作り、端末間のファイル共有機能やクラウドストレージなどでスマホに渡して、アプリの「取り込み」機能で読み込む。
- 保存先はブラウザ内ストレージ（IndexedDB）。
- 外部サーバーへの送信は行わない（アナリティクス・外部 API も、導入する場合は先にルールを更新）。
  - 音声がない単語・例文を読み上げるブラウザ内蔵の音声合成（Web Speech API）は、端末の中で合成する声（`localService` が真の声）だけを使う。外部のサーバーで合成する声は、教材の文を送ることになるため使わない（`docs/specs/study-cards.md` 9 章）。
- 将来、複数端末の同期が必要になったら「認証付きの非公開ストレージ」を追加機能として検討する（その時点でルールを更新）。

## 4. PWA / 端末まわりの必須要件

- **オフラインで完全に動作する**こと（Service Worker でアプリ本体をキャッシュする）。
- 起動時に `navigator.storage.persist()` を要求する。
- iOS Safari ではホーム画面に追加しないとデータが消えることがあるため、未追加の場合はアプリ内で案内する。
- 学習記録は**エクスポート / インポート**できること（端末にしかデータがないため、バックアップ手段は必須）。
- スマホ縦画面・片手操作を基準に UI を作る。PC でも動けばよい。

## 5. カスタマイズ性

- 教材は人が読める形式（JSON / CSV）で持ち、形式は `docs/CONTENT_FORMAT.md` に文書化する。
- 元の音声ファイルは加工しない。1 ファイルに複数項目を収録した音声にも対応するため、項目ごとの再生は「ファイル名＋開始秒〜終了秒」で指定できるようにする。
- **教材データ**と**学習記録**は分けて保存する。教材を差し替えても記録が壊れないよう、項目は安定した `id` で参照する。
- 学習アルゴリズムの設定（復習間隔、習得の基準など）は設定値として外に出し、コードにハードコードしない。

## 6. 公開リポジトリとしての衛生

- ライセンスは MIT（`LICENSE`）。デモ教材（`demo/`）だけは CC BY-SA 4.0（11 章）。
- API キー・個人情報・ローカルの絶対パスをコードに書かない。
- **開発者個人の環境・端末の情報を公開ファイルに書かない。** 例: 使っている OS・PC・スマホの機種、インストール済みのツールやバージョン、ユーザー名（著作権表示とリポジトリの URL に使う GitHub アカウント名は除く）、ディレクトリ構成。設計理由は「自分の環境ではこうだから」ではなく、一般的な理由で書く。動作要件として必要なもの（例: 対応ブラウザ、必要な Node.js のバージョン）は、要件として書いてよい。
- README に「教材データは同梱していない（11 章のデモ教材を除く）。自分で用意したデータを取り込んで使う」と明記する。あわせて「コードは MIT、`demo/` は CC BY-SA 4.0」と書く。
- ローカルの教材は全て `data/` 以下に置き、`.gitignore` で丸ごと除外する。`data/` の外に教材を置かない。

## 7. 公開ドキュメントとローカルドキュメントの分離

| | 公開ドキュメント（`docs/`） | ローカルドキュメント（`private/`、Git 管理外） |
|---|---|---|
| 書くこと | 汎用の単語帳アプリとしての設計・ルール | 自分の教材に関すること全て |
| 例 | 教材パック形式、学習アルゴリズム、画面設計 | 手元の教材の種類・形態・規模、教材に合わせた作業計画、教材パックの作り方 |

- 公開されるファイル（ドキュメント・コード・コミットメッセージ・Issue）には、**手元の教材を推測できる情報を書かない**。対象は書名・出版社だけでなく、教材の種類や形態（例: どんな形式のデータを持っているか、持っていないか）、規模、フォルダ名・ファイル名なども含む。
- 公開ドキュメントの設計理由は「汎用ツールとして必要だから」の形で書く。自分の教材の都合で決めたことは `private/` に書く。
- `CLAUDE.local.md`（Git 管理外）から `private/` を参照する。

## 8. コミット前の著作権レビュー

全てのコミットは、次の 2 段階のチェックを通す。

| 段階 | 仕組み | 内容 |
|---|---|---|
| 意味のレビュー | `copyright-reviewer` エージェント（`.claude/agents/`） | 教材の内容・教材を推測できる情報・公開経路への混入・第三者素材のライセンスを確認し、PASS ならステージ内容に対する承認を記録する（`scripts/approve-copyright-review.sh`） |
| 機械的チェック | git フック（`scripts/git-hooks/`） | `data/`・`private/`・メディアファイルの混入（デモ教材の音声 `demo/audio/` だけは通す。11 章）、禁止語（非公開リスト）、承認の有無を確認し、問題があればコミットを止める |

- 禁止語リストは Git 管理外（`.git/info/copyright-denylist`）に置く。
- フックの回避（`--no-verify` など）は禁止。
- 承認を記録するスクリプトは、Claude Code のプロジェクト設定（`.claude/settings.json`）で確認なしに実行できるよう許可している。copyright-reviewer が PASS のときに止まらず記録できるようにするため。許可はエージェントごとに分けられないので、メインのエージェントが自分で実行しないことは、`CLAUDE.md` の「承認マーカーを自分で書き込まない」という決まりで守る。スクリプトを書き換えて別の処理を確認なしで動かせないよう、スクリプトの編集は設定で禁止している（直すときは人が編集する）。
- 新しい環境で clone した場合は `git config core.hooksPath scripts/git-hooks` を実行してフックを有効にする。

## 9. 技術スタック

| 役割 | 採用 | 選定理由 |
|---|---|---|
| ビルド | Vite | 標準的で高速。静的サイトとして配信できる |
| 言語 | TypeScript | 教材パック形式などのデータを型で検証できる |
| UI | React | 情報・ライブラリが最も多く、カスタマイズ時に調べやすい |
| スタイル | 普通の CSS（CSS Modules） | 追加ライブラリ不要。小規模アプリには十分 |
| 画面遷移 | React Router（HashRouter） | 定番で戻る操作にも対応する。ハッシュ形式の URL なら配信先のパス構成に依存しない |
| PWA | vite-plugin-pwa | Service Worker とマニフェストを生成し、オフライン動作を実現する |
| 端末内保存 | Dexie.js（IndexedDB） | 音声 Blob を保存でき、スキーマ変更（マイグレーション）が容易 |
| zip 展開 | fflate | 軽量・高速で、スマホ上での展開に向く |
| 区間再生 | Web Audio API でデコード・切り出し、`<audio>` 要素で再生（どちらもブラウザ標準） | 区間だけを WAV に切り出して最後まで鳴らすため、停止位置がずれない（`<audio>` 要素で途中から途中まで鳴らすと iOS で停止位置がずれやすい）。Web Audio API で鳴らすと、iOS ではアプリを離れて戻った後に音が出なくなる不具合がある |
| 機械の音声 | Web Speech API（ブラウザ標準。端末の中で合成する声だけ） | 音声がない単語・例文を、データの準備なしに読み上げられる |
| テスト | Vitest | Vite と設定を共有できる |
| テスト用の IndexedDB | fake-indexeddb（開発時のみ） | Node 上のテストで IndexedDB を再現し、Dexie を使う処理をテストできる。アプリ本体には含まれない |
| 整形・静的解析 | Biome | 整形と静的解析を 1 つのツールで行える |
| パッケージ管理 | npm | Node.js 標準のパッケージマネージャーで、追加のツールが要らない |

- 採用するライブラリは、公開リポジトリと両立するオープンソースライセンス（MIT など）のものに限る。
- この表はアプリ本体とその開発に使うもの。デモ教材の音声を作る道具（11 章）は、アプリにも配信物にも含めないので、この表の対象外とし、11 章で扱う。
- ここにないライブラリを追加する場合は、先にユーザーに確認し、この表を更新する。

## 10. 開発の進め方

- 小さく作ってスマホの実機で確認しながら進める。
- 優先順位: **単語の学習** → 学習記録・復習 → その他の教材形式への対応。
- 大きな設計判断はドキュメントに残す（何を選び、なぜそうしたか）。汎用的な判断は `docs/`、教材固有の判断は `private/`。
- 画面構成・フォルダ構成・データ構造・実装の順番は `docs/ARCHITECTURE.md` に従う。
- 実装の区切りとコミットの前に、`code-reviewer` エージェント（`.claude/agents/`）でコードレビューを行う。著作権のチェック（8 章）とは別に行う。

## 11. 公開するデモ教材

アプリと一緒に、デモ用の教材パックを公開する。この章には決まりだけを書き、作り方の手順・道具・画面は `docs/specs/demo-pack.md` に書く。

- **目的**: 他の人が、教材パックの形式（`docs/CONTENT_FORMAT.md`）と作り方の見本にして、自分のデータを作れるようにする。あわせて、教材を用意しなくてもアプリを試せるようにする。
- **公開の形**: アプリの「デモを試す」ボタンで読み込む。中身はふつうの教材パックと同じで、取り込んだ後は削除もできる。
- **規模**: 20 語 × 2 ユニット（40 語）。

### 材料（オープンなライセンスのものと自作のものだけ）

| 中身 | 材料 | 材料のライセンス | デモでの扱い |
|---|---|---|---|
| 見出し語と並び | NGSL（New General Service List）1.2 の `NGSL_12_stats.csv`（`SFI Rank` 列） | CC BY-SA 4.0 | 権利の対象は単語そのものではなく一覧（選び方・順位）。デモはこれを改変したものとして CC BY-SA 4.0 にする |
| 訳 | EJDict-hand（英和辞書）の訳語をそのまま使う（言い換えない。下の「訳の決まり」） | CC0 1.0 | 訳語そのものは条件なしで使える |
| イディオム | EJDict-hand の熟語の項目（見出しに空白を含む項目）。句は見出しのまま、意味はその項目の訳語から選ぶ | CC0 1.0 | 訳語そのものは条件なしで使える |
| 例文・例文の訳 | デモのために新しく作る | — | デモのライセンス（CC BY-SA 4.0） |
| 単語・例文の音声 | 読み上げモデル Kokoro-82M（声は `af_heart`）で合成する。実際に使うのは kokoro-onnx が配布している変換版 | Apache-2.0（Kokoro-82M のリポジトリ全体のライセンス表記。声のファイルだけのライセンス表記はない）。モデルカードに、生成した音声の利用を制限する記載はない | 生成した音声はデモのライセンス（CC BY-SA 4.0） |

- デモ教材のうち権利が生じる部分（選んで並べた一覧・例文・例文の訳・音声など）に CC BY-SA 4.0 を適用する。生成した音声など、権利が生じるかどうかがはっきりしない部分も、同じライセンスで配布する。
- 材料のライセンスは、使う時点で配布元の表記をもう一度確かめる。取得元の URL（リダイレクト先のファイル名も）、取得日、取得したファイルを確かめる値（SHA-256）を `demo/README.md` に記録する。読み上げモデルと声のファイル（`kokoro-v1.0.onnx`・`voices-v1.0.bin` など、実際に使ったもの）も同じように記録する。

### 手元の教材を混ぜないための決まり

教材の選定・順序・訳・例文・音声のどれもデモに混ざらないよう、それぞれを次の材料に限り、守れたことをできるだけ道具で確かめる。見出し語と並びは NGSL、訳とイディオムは EJDict-hand、例文は新しく作ったもの、音声は合成したもの。

- デモの中身を**作る段階では**、手元の教材（`data/`・`private/`）を使わない・参照しない。単語の選び方を手元の教材に合わせて変えることもしない。例外は、コミット前の照らし合わせ（読むだけ）だけ。
  - **作る作業は、git worktree（同じリポジトリを別のフォルダに展開したもの）で行う。** Git 管理外のファイル（`data/`・`private/`・`CLAUDE.local.md` など）が入らないので、そこで開いた作業の場（生成 AI の会話とそのサブエージェントを含む）に、手元の教材の情報が渡らないようにできる。
  - worktree の作り方と、手元の情報を遮るための設定（自動メモリを切る、元のリポジトリの `data/`・`private/` などを読めなくする、置き場所の決め方）は `docs/specs/demo-pack.md` 2 章に従う。元のリポジトリの Git 管理外のファイルを写さない。
  - worktree は作る場所としてだけ使う。照らし合わせとコミットは、元のリポジトリで行う（今のコミットの手順・git フック・承認の記録をそのまま使うため）。
  - 作る担当には、NGSL の語、その語の EJDict-hand の項目、教材パックの形式（`docs/CONTENT_FORMAT.md`）だけを渡す。
- ほかの辞書・単語集・教科書・Web サイトの訳・例文・イディオムを写さない。生成 AI に手伝わせるときも、辞書でよく見る決まった例文は使わない。生成 AI を使ったことと、与えた指示の要点を `demo/README.md` に書く。
- **訳とイディオムの決まり**:
  - 各用法の訳（`meanings[].meaning`）は、その見出し語の EJDict-hand の項目に載っている訳語から選んで並べる。
  - イディオムの句（`idioms[].phrase`）は、EJDict-hand の熟語の項目の見出しと一致させ、意味（`idioms[].meaning`）はその項目の訳語から選ぶ。見出し語を含む熟語の項目がなければ、その語にはイディオムを付けない。訳語の文字は変えず、言い換えない。訳語の取り出し方（記号の扱い・区切り方）は `docs/specs/demo-pack.md` の手順に従う。
  - 例文の訳の太字の部分（`exampleTranslationTarget`）は、その用法の訳語、または訳語の活用した形にする。
  - EJDict-hand の訳語が古い・硬いときは、載っている中から自然なものを選んで対応する。誤字のある訳語は使わない（見つけた誤字は、道具の「使わない訳語」の一覧に入れる）。
- **自分で決めるもの**: 品詞（決まった一覧から選ぶ）、用法の分け方と並び、例文、例文の訳（太字以外の部分）、`exampleTarget`（例文の一部）。どれも新しく作り、ほかの資料から写さない。
- **道具で確かめる**: 訳とイディオムの決まりと、選定・順序（見出し語・`id`・並び・ユニットの分け方が NGSL の順位どおりか）を確かめる道具を `scripts/` に置く。記録を信じるのではなく、`demo/` を変えたコミットのたびに、ステージされた内容で道具を実行して確かめる（git フック）。使う EJDict-hand の版は固定し、だれでも同じ確かめをやり直せるようにする。
- **音声の出どころを記録する**: 音声を作る道具は、生成の記録（読み上げた文・声・モデルのファイル・圧縮の道具の版・出力のファイルの SHA-256）を書き出す。記録にない音声はコミットしない。道具には、記録の文から作り直して長さと区間が合うかを確かめる動作を付ける。記録の文と区間が `demo/items.json` と一致することも確かめる（中身を直した後に古い音声が残らないように）。
  - 残る危険: 記録との一致で確かめられるのは「記録に書かれたとおりに作った」ことまでで、記録そのものが正しいことは、作り直しの確かめとレビューに頼る。
- **手元の教材との照らし合わせ**: コミット前に、デモの中身が手元の教材とその関連データを流用・言い換えしたものでないことを、手元で機械的に照らし合わせて確かめる。照らし合わせは元のリポジトリ（worktree ではない場所）で行う。手順と結果は公開しない（`private/` に置く）。
  - 照らし合わせたときの `demo/items.json` の SHA-256 を、結果と一緒に記録する。
  - 照らし合わせで似たものが見つかったら、直さずに捨て、手元の教材を参照せずに作り直す。作り直したら、照らし合わせをやり直す。照らし合わせを行う作業の場では、デモを編集しない。

### 単語の選び方

- NGSL 1.2 の `SFI Rank` で **1001〜1040 番**の 40 語を使い、順位の順に 20 語ずつユニット 1・2 に分ける。
  - 範囲は先に決め、中身を見て変えない。決まった規則で機械的に選ぶことで、どの教材とも関係なく選んだことが分かり、同じ手順でだれでも作り直せるようにする。
- 固有名詞・略語など、単語帳の見本に向かない語があれば飛ばして次の順位の語を使い、飛ばした語と理由を `demo/README.md` に書く（決めた時点の NGSL 1.2 では、この範囲に該当する語はない）。イディオムの有無などの中身を理由に、範囲や語を変えることはしない。
- ユニット名は「デモ 1」「デモ 2」とする。

### 作り方の決まり

- 教材パックの形式の項目は、どれも 1 回以上使う（用法が複数の語、イディオム、`exampleTarget`・`exampleTranslationTarget`、`audio`・`exampleAudio` の区間指定、`license`・`attribution` など）。形式の見本にするため。
- 用法は 1 語あたり 1〜3 つ。例文は 1 用法に 1 文、10〜15 語程度の自然な英文にする。
- 音声の形式（1 ファイルに複数の項目を入れ、区間で指定する）:

| 種類 | 形式 | まとめ方 |
|---|---|---|
| 単語 | AAC-LC（`.m4a`）・モノラル・64 kbps（単語は短く、子音の聞き分けが大事なので、例文より高くする） | ユニットごとに 1 ファイル |
| 例文 | AAC-LC（`.m4a`）・モノラル・24 kbps | ユニットごとに 10 文前後ずつ |

  - 区間と区間の間には 0.4 秒の無音を入れる。AAC は圧縮のときに頭に短い無音が足され、区間が後ろにずれることがあるため。区間は圧縮後のファイルで測り直し、並べた位置と測った位置の広いほうに、前 0.05 秒・後ろ 0.15 秒の余裕を足す。
  - HE-AAC は使わない。高い音域を後から補って作る方式のため、低いビットレートでは声が二重に聞こえるようなひずみが出やすい。
  - 1 ファイルに複数の項目を入れるのは、ファイル数を抑えつつ、区間で指定する形式の見本にするため。

### 音声を作る道具

- 道具は `scripts/` の下に MIT で公開し、他の人も使えるようにする。開発のときだけ使い、アプリ本体と配信物には含めない。
- 道具が使うライブラリ（読み上げの実行に kokoro-onnx〈MIT〉、その依存の espeakng-loader〈MIT。espeak-ng を含むことがある〉・espeak-ng・phonemizer〈GPL-3.0-or-later。版によっては phonemizer-fork〉など。固定した版での名前を書く）・圧縮に使う ffmpeg（内蔵の AAC エンコーダ。LGPL-2.1-or-later。GPL を含むビルドでも、別のプログラムとして呼び出すだけなので道具と生成した音声には及ばない。nonfree のエンコーダは使わない）とモデル・声のファイルは、使う人が各自インストールする。リポジトリには入れない（git フックで止める）。
  - ほかに onnxruntime（MIT）・numpy（BSD）・音声の読み書きのライブラリなどを使う。どれも、固定した版でのライセンスを確かめて書く。
  - GPL は、生成した音声には及ばない（GPLv3 2 条）。道具のスクリプトは、GPL と両立する MIT にし、GPL のライブラリを同梱しないので、MIT で公開できる。
- 依存はバージョンを固定して書く。必要な道具は動作要件として書き、特定の OS に付属するコマンドに頼らない。
- 作り直せるように、生成の記録には道具・ライブラリ・ffmpeg・モデルの版の番号と、ファイルの SHA-256 を書く。これは 6 章の「インストール済みのツールやバージョンを書かない」の例外とする。ただし、ビルドの設定・インストール先のパスなど、開発者の環境が分かる情報は書かない。

### チェック

- git フックは、デモ教材の音声だけを通す。通すのは次をすべて満たすファイルに限る。
  - `demo/audio/` の直下（下にフォルダを作らない）にあり、名前が `demo-` で始まる `.m4a`
  - 1 ファイル 1 MB 以下
  - `demo/items.json` から使われている
- `.gitignore` は音声ファイルを除外しているので、`demo/audio/demo-*.m4a` だけを例外にする。
- モデル・声などのファイル（`.onnx`・`.bin`・`.pt`・`.pth`・`.safetensors`・`.npz`・`.npy` など）は、どこにあっても止める。
- git フックは、ステージされたデモの音声の SHA-256 が、音声の生成の記録にあることも確かめる。判定は、作業中のファイルではなくステージされた内容で行う。
- ビルドのあと、配信物（`dist/`）に入っている教材が、デモの zip だけであることを確かめる（3 章）。
- `copyright-reviewer` は、デモ教材の変更がこの章の決まりに沿っているかも確かめる。確かめる点は、材料・出典・帰属表示、手元の教材の手がかりがないこと、照らし合わせの記録の SHA-256 がステージされた `demo/items.json` と一致すること。訳とイディオムの確かめは git フックが行う。

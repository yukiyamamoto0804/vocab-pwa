## 1. パックの中身

- パックの `id` は `demo-ngsl`、`title` は「デモ（NGSL）」。
- ユニットは 2 つ（「デモ 1」「デモ 2」）。NGSL 1.2 の `SFI Rank` 1001〜1040 番の 40 語を、順位の順に 20 語ずつ分ける。
  - 見本に向かない語を飛ばした場合（`docs/RULES.md` 11 章）は、次の順位の語を足して 40 語にし、順位の順に 20 語ずつ分ける。
- 単語の `id` は `ngsl-<SFI Rank>`（例: `ngsl-1001`）。作り直しても変えない（学習記録を引き継ぐため）。
- `demo-ngsl` はデモ専用の `id` とする。利用者が同じ `id` のパックを作っていた場合、「デモを更新」で上書きされることがある（`docs/CONTENT_FORMAT.md` の取り込み直しと同じ扱い）。
- `manifest.json` に `license`（`CC BY-SA 4.0`）と `attribution`（`docs/RULES.md` 11 章の出典の表記、ライセンスへのリンク、保証しないことの一言）を書く。デモを作り直したら `createdAt` を更新する。
- 形式の項目は、どれも 1 回以上使う（`docs/RULES.md` 11 章）。イディオムは、40 語のうち EJDict-hand に使える熟語の項目がある語に付ける（決めた時点の版では 16 語にある）。

## 2. 作る手順

作る作業は git worktree で行い、コミットは元のリポジトリで行う。worktree は作る場所としてだけ使う。

### worktree の用意

1. 道具（3・4 章）をコミットした後の `main` から、元のリポジトリで `git worktree add --detach <パス> main` を実行する（ブランチは作らない。コミットは元のリポジトリで行うため）。
   - パスはリポジトリの外で、上のフォルダに `CLAUDE.md`・`CLAUDE.local.md` がなく、英数字だけからなる場所にする（Claude Code は上のフォルダの `CLAUDE.md`・`CLAUDE.local.md` も読み込むため。また、英数字以外の文字を含むパスは、Claude Code のプロジェクトごとのフォルダ名が置き換えられ、ほかのプロジェクトと重なることがあるため）。
   - Claude Code の組み込みの worktree 機能（リポジトリの中に作るもの）は使わない。
2. worktree に、Claude Code の設定（`.claude/settings.local.json`。Git 管理外）を置く。
   - 自動メモリを切る（同じリポジトリの worktree では、自動メモリが共有されるため）。
   - 元のリポジトリの `data/`・`private/`・`CLAUDE.local.md`・`.git/info/` を読むことを禁止する。
3. worktree の作業の場（生成 AI の会話）は新しく始める。元のリポジトリの以前の会話を開き直さない。
4. Git 管理外のファイル（`data/`・`private/`・`CLAUDE.local.md` など）は、worktree に写さない。

### 作る（worktree の中で行う）

5. NGSL 1.2 の `NGSL_12_stats.csv` を、3 章の手順で取得する。
6. EJDict-hand を、決めた版（3 章）で取得する。
7. 40 語それぞれについて、EJDict-hand の見出し語の項目と、使える熟語の項目を、3 章の手順で取り出した訳語の候補と一緒に一覧にする（道具の動作の 1 つ）。
8. 中身を作る。作る担当には、7 の一覧と、教材パックの形式（`docs/CONTENT_FORMAT.md`）だけを渡す。
   - 作るもの: 用法の分け方、品詞、訳（訳語の候補から選ぶ）、例文、`exampleTarget`、例文の訳と太字の部分、イディオム（熟語の項目から選ぶ）。
   - 生成 AI に手伝わせるときに与えた指示の要点を、`demo/README.md` に書く。
9. 音声を作る道具（4 章）で、単語と例文の音声を作り、`audio`・`exampleAudio` を書き込む。
10. 中身を確かめる道具（3 章）を通す。`demo/README.md`・`demo/LICENSE` を書く。

### 照らし合わせとコミット（元のリポジトリで行う）

11. worktree の `demo/` を、元のリポジトリの `demo/` に写す。
12. 元のリポジトリで、手元の教材との照らし合わせを行う（手順は非公開）。
    - 似たものが見つかったら、その項目を捨てる。worktree の作業には、捨てる項目の単語の `id`・用法の番号・項目名だけを伝える（似ていた手元の文や理由は伝えない）。worktree で 8 からやり直し、11 から進め直す。
13. 元のリポジトリで、今のコミットの手順（`CLAUDE.md`）どおりにステージし、コミットする。git フック・禁止語リスト・copyright-reviewer・承認の記録は、今のまま働く。
14. 済んだら worktree を消す（`git worktree remove`）。

- 中身を直したら、9（例文や単語を変えたとき）・10・12 をやり直す（`demo/items.json` が変わると、照らし合わせの記録や音声の記録と合わなくなるため）。

## 3. 中身を確かめる道具

`scripts/demo/check-demo.mjs`（Node.js。git フックから呼ぶため、アプリの開発に使う Node.js だけで動かす）。`demo/items.json` と `demo/manifest.json` を読み、訳・イディオム・選定・順序の決まり（`docs/RULES.md` 11 章）を守れているかを確かめる。

### 材料の版と取得

- NGSL 1.2 の CSV と EJDict-hand は、どちらも版を固定する。NGSL は取得元の URL と SHA-256、EJDict-hand は配布元のリポジトリのコミットと使うファイルの SHA-256 を、道具の中と `demo/README.md` に書く。
- 道具は、固定した版を配布元から取得して、Git 管理外の `.cache/` に置く。SHA-256 が違えば止める。
- `.cache/` に材料がなく、取得もできない（オフラインなど）ときは、確かめずに通すのではなく止める。

### 選定・順序の確かめ

- 各単語の `id` が `ngsl-<SFI Rank>`、`word` がその順位の見出し語（`Lemma`）と同じである。
- 単語の並びが順位の順で、1001 番から 40 語（飛ばした語を除く）が抜けなく入っている。飛ばした語は、道具の中の一覧と `demo/README.md` の両方に書き、一致させる。
- ユニットが 2 つで、並びの順に 20 語ずつに分かれている。

### 訳語の取り出し方

方針: 目的は「訳が EJDict-hand の文字列から来ていること」を確かめることなので、候補は多めにできてよい。ただし、EJDict-hand にない文字列（言葉の途中を削ったものなど）は候補に入れない。

見出しごとに、次の順で訳語の候補を作る。

1. 見出しの欄（タブの前）を `,` で区切り（前後の空白は削る）、確かめる見出し（単語なら見出し語、イディオムなら句）と完全に一致する（大文字・小文字も同じ）ものがある行を探す。
2. 訳の欄を ` / ` で区切る。行全体で括弧の対がそろっていれば、区切った部分をそのまま使う。そろっていなければ、区切った部分ごとに対がそろっているかを判定し、そろっていない部分だけを捨てる（行全体は捨てない。括弧が ` / ` をまたぐ行があるので、先に行全体で試す）。
3. 括弧を、対ごとに中身と一緒に消す。順番は `《》` → `()`・`（）`・`[]`・`〈〉`・`{}`（入れ子は内側から）。消した位置は覚えておく（6 で使う）。
4. `『』` は、記号だけを消し、中の言葉は残す（大事な訳語の印のため）。
5. `;`・`,`・`、`・`・` で区切り、前後の空白を削る。`=` で始まるもの、日本語の文字を含まないもの、空になったものは捨てる。
6. 先頭の「…」は外す。候補の先頭にある助詞 1 つ（を・に・が・の・と・で・から・へ・より）で、その前が 3 で消した括弧か「…」だけだったものは、外した形と外さない形の両方を候補にする。それ以外の位置の助詞は外さない。
7. 「使わない訳語」の一覧（誤字・英語の混ざったものなど。道具の中に書く）にあるものを捨てる。

- 40 語と、デモで使う熟語について、作った候補の一覧をテストの期待値として固定する（`scripts/demo/` のテスト）。期待値には、壊れた文字列（言葉の途中を削ったもの）が入っていないことを確かめる。EJDict-hand の版を変えるときは、期待値を見直す。
  - `npm test`（CI を含む）がネットにつながらなくても動くよう、テストに使う EJDict-hand の行だけを固定データとして `scripts/demo/fixtures/` に置く（EJDict-hand は CC0 なので置ける。出典を書く）。NGSL のデータは固定データに置かず、選定・順序の確かめのテストは自作のダミーデータで行う。

### 確かめること（訳とイディオム）

- 各用法の `meanings[].meaning` を「、」で区切った一つ一つが、その見出し語の訳語の候補のどれかと一致する。訳語どうしをつなぐ記号は「、」だけにする。
- 各イディオムについて:
  - `phrase` が EJDict-hand の熟語の項目の見出しと一致する。その見出しは空白を含み、見出し語を 1 つの単語として含む。見出しに括弧があるもの、訳が `=…` だけのものは使わない。
  - `meaning` を「、」で区切った一つ一つが、その項目の訳語の候補のどれかと一致する。
- `exampleTranslationTarget` が `exampleTranslation` にそのまま含まれている。
- `exampleTranslationTarget` が、その用法の訳語のどれかの活用した形になっている。判定は次のとおり。
  - 訳語と一致すれば合格。
  - 訳語の末尾が活用する語尾（動詞・形容詞・形容動詞の語尾の一覧。「する」「な」などを含む。道具の中に書く）なら、長いものから順に当てて、それを除いた部分を語幹とする。
  - 語幹が「漢字かカタカナを 1 字以上含む」か「ひらがな 2 字以上」なら、太字が語幹で始まり、残りがひらがなだけのとき合格（例: 買う → 買った、適切な → 適切に）。
  - それ以外の訳語は、訳語と一致する場合だけ合格にする。
- `exampleTarget` が `example` にそのまま含まれている。
- 誤字のある訳語は、道具では見分けられない。作る担当とレビューで目で確かめ、見つけたら「使わない訳語」に足す。

### 音声の記録との一致

- `demo/audio-sources.json`（4 章）の各項目の読み上げた文が、`demo/items.json` の `word`・`example` と一致し、区間が `audio`・`exampleAudio` と一致する。`items.json` から使われている音声のファイルが、すべて記録にある。

### 実行

- `node scripts/demo/check-demo.mjs [demo フォルダのパス]`。合格なら 0、不合格なら理由を出して 0 以外で終わる。
- `node scripts/demo/check-demo.mjs --candidates` で、2 章 7 の一覧（訳語の候補）を書き出す。
- git フックは、ステージされた `demo/` の JSON を一時フォルダに取り出して実行する（7 章）。

## 4. 音声を作る道具

`scripts/demo/` に置く（Python）。`demo/items.json` から単語と例文を読み上げ、区間を測って `audio`・`exampleAudio` を書き込む。

- 読み上げ: Kokoro-82M（kokoro-onnx が配布している変換版のモデル `kokoro-v1.0.onnx` と声 `voices-v1.0.bin`）、声は `af_heart`、等速。モデルと声のファイルは、使う人が各自取得する。取得したリリースのタグ名（例: `model-files-v1.1`）と SHA-256 を `demo/README.md` に書く。
- 圧縮: ffmpeg の内蔵の AAC エンコーダ（`-c:a aac -profile:a aac_low`）で AAC-LC（`.m4a`）にする。単語は 64 kbps、例文は 24 kbps、モノラル（`docs/RULES.md` 11 章）。ffmpeg は使う人が各自インストールする。
  - 内蔵のエンコーダの音質が、24 kbps の例文で十分かは、作るときに聞いて確かめる。足りなければビットレートを見直す（RULES を更新する）。
- ファイル名: 単語は `demo-words-<ユニット>.m4a`、例文は `demo-examples-<ユニット>-<n>.m4a`。
- 並べ方と区間の測り方は、`docs/RULES.md` 11 章の決まり（0.4 秒の無音、測り直し、前 0.05 秒・後ろ 0.15 秒の余裕）に従う。
- 生成の記録: `demo/audio-sources.json` に、次を書く。
  - 音声ファイルごとの SHA-256 と長さ、中に入れた項目（単語の `id` と用法の番号、読み上げた文、区間）
  - 声、モデルと声のファイルの SHA-256、ffmpeg の版の番号、道具の版
  - ffmpeg のビルドの設定やインストール先のパスなど、開発者の環境が分かる情報は書かない（`docs/RULES.md` 6 章）。
- 確かめの動作: 記録の文を読み上げ直して並べ、記録の音声ファイルと長さ・区間が合うか（差が 0.05 秒以内か）を確かめる。圧縮の結果はバイト単位では一致しないことがあるので、SHA-256 ではなく長さと区間で比べる。
- 依存（読み上げのライブラリ、音声の読み書きのライブラリなど）は、バージョンを固定して `scripts/demo/` に書く。

## 5. 置き場所とビルド

```
demo/
├── manifest.json
├── items.json
├── audio/                 demo-*.m4a だけ（下にフォルダを作らない）
├── audio-sources.json     音声の生成の記録（4 章）
├── README.md              出典・改変の表示・作り方・他の人向けの説明
└── LICENSE                CC BY-SA 4.0 の全文
scripts/demo/              中身を確かめる道具（Node.js）・音声を作る道具（Python）
```

- ビルドのとき、`demo/` の `manifest.json`・`items.json`・`audio/`・`README.md`・`LICENSE` を zip にまとめ（fflate を使う）、配信物に `demo/demo-ngsl.zip` として入れる。zip はコミットしない。開発サーバーでも同じ URL で配る。この処理は Vite のプラグインとして `scripts/build/` に置き、`vite.config.ts` から読み込む。
- `demo/` は Biome の対象から外す（`biome.json`）。道具が書き出す JSON の整形を Biome に変えられると、`demo/items.json` の SHA-256 が変わり、照らし合わせの記録や埋め込んだハッシュと合わなくなるため。
- アプリからは、配信物の置き場所からの相対 URL（`demo/demo-ngsl.zip`）で受け取る（配信先のパス構成に依存しないため）。
- ビルドのとき、`demo/manifest.json` の `title`・`createdAt`・`license`・`attribution` と、`demo/items.json` の SHA-256 を、Vite の `define` でアプリに埋め込む（6 章の説明のシートで zip を受け取る前に表示するためと、更新の判定のため）。出典の文は `manifest.json` の 1 か所だけに書く。
- アプリの側でデモを受け取って取り込む処理は `src/features/demo/` に置き、取り込みそのものは `features/content-pack/` の処理を使う。
- デモの zip は、Service Worker で前もってキャッシュしない（アプリ本体を軽く保つため）。オフラインで「デモを試す」を押したときは、ネットにつないでから試すよう伝える。
- ビルドのあと、`dist/` に入っている教材になりうるファイル（`.zip`・音声の拡張子・`manifest.json`・`items.json`）が、デモの zip だけであることを確かめる。PWA のマニフェスト（`manifest.webmanifest`）は対象外。この確かめは `vite build` の後に実行するスクリプト（`scripts/build/`）にし、`npm run build` に含める（CI も同じコマンドで確かめられる）。

## 6. 画面

### デモを試す

- ホームに「デモを試す」ボタンを置く。教材パックが 1 つもないときは目立たせ、あるときは一覧の下に小さく出す。
- 押すと、説明のシートを開く。中身は、デモの説明（20 語 × 2 ユニット・形式の見本であること）、ライセンスと出典（ビルドのときに埋め込んだもの）、「読み込む」ボタン。
- 「読み込む」で `demo/demo-ngsl.zip?v=<埋め込んだ SHA-256 の先頭 12 文字>` を受け取り（ブラウザのキャッシュに残った古い zip を受け取らないため）、ふつうの取り込みと同じ処理（検証・保存）で取り込む。取り込んだらユニット一覧を開く。
- 「デモを試す」から取り込んだときだけ、埋め込んだ `items.json` の SHA-256 を `packs` の `demoItemsSha256` に保存する（取り込むときに計算しない。計算に使う機能は HTTPS でしか使えないため）。ふつうの取り込みでは保存しないので、デモの zip をふつうに取り込むと「デモを更新」が出る（安全側の動き）。
- `id` が `demo-ngsl` のパックがすでにあるとき:
  - 保存した `demoItemsSha256` が、埋め込んだ SHA-256 と同じなら、ボタンを「デモを開く」にして、そのパックのユニット一覧を開く。
  - 違えば、ボタンを「デモを更新」にする。押すと、ふつうの取り込みの更新と同じ処理で取り込み直す（単語の `id` が変わらないので、学習記録は引き継がれる）。

### パックの情報

- ユニット一覧に「このパックについて」を置き、パックの名前・作成日・`license`・`attribution` を表示する。どれも、あれば表示する。
- `attribution` の中の URL は、`https://` か `http://` で始まるものだけをリンクにする（他の人が作ったパックの中身は信用できない入力として扱う）。URL は空白・`(`・`)`・`（`・`）`・`、`・`。` の手前で切り、そのうえで末尾の `.`・`,` を外す。リンクは新しいタブで開き、`rel="noopener noreferrer"` を付ける。
- デモに限らず、すべてのパックで表示する（他の人のデータを使って作ったパックの帰属表示も、取り込んだ後に見えるようにするため）。

## 7. チェック

- git フック（`docs/RULES.md` 11 章）。判定は、作業中のファイルではなくステージされた内容（`git show :<パス>`）で行う。JSON の読み取りと SHA-256 の計算が要るので、フックから Node.js のスクリプト（`scripts/git-hooks/` の下）を呼ぶ。
  - `demo/` の変更がステージされていたら:
    - ステージされた `demo/` の JSON で、中身を確かめる道具（3 章）を実行する。
    - `demo/audio/` の直下の `demo-*.m4a` で、1 ファイル 1 MB 以下、ステージされた `demo/items.json` から使われていて、SHA-256 がステージされた `demo/audio-sources.json` にあるものだけを通す。
  - モデル・声などのファイル（`.onnx`・`.bin`・`.pt`・`.pth`・`.safetensors`・`.npz`・`.npy` など）は、どこにあっても止める。
